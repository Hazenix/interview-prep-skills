# 简历面试问题文档

面向想快速备题的候选人。站在只看得到指定简历条目的面试官视角出题，再根据候选人的选择决定是否写回答。处理项目/实习经历和专业技能，不要求提供整份简历，也不限技术栈。

## 输入

- 必需：候选人指定的一条或多条简历条目。可以只给项目/实习经历，或只给专业技能。缺少条目时请候选人提供，不要求补齐其他部分。
- 可选：岗位 JD、候选人级别、用于回答的项目代码、项目文档或补充说明。级别未提供时直接出题，不开启模拟面试的配置流程。
- 产出前确认一次：**只要问题，还是问题和回答一起产出？** 用户已说明时直接采用，不重复询问。需要回答但缺少项目材料时，一次性提示可提供哪些材料；用户不提供也继续，在无法证实的回答处标“待补充”。

## 先出题，再写答案

1. **出题阶段**读取指定的简历条目和 [常见问题](references/common-questions.md)；专业技能部分还可读取用户提供的 JD。即使代码、项目文档或补充说明已经给出，也先不读取、不检索其内容，避免提出不是从面试官视角出发的伪面试问题。把全部主问题和追问写成纯问题 Markdown 文件，文件成功保存才算出题完成；这份文件就是固定的问题稿，不要求候选人逐题确认。
2. 输入包含项目或实习经历时，从常见问题文件中选出适用于当前经历的问题，同一段经历的整体问题只问一次，再结合简历逐条深挖；库中新增的问题也按此规则纳入。JD 不参与项目/实习出题。把简历所写职责视为候选人的职责；可以问简历没有给出答案的常见背景问题，不预设答案。
3. 专业技能题以条目写出的技能为主，参考常见问题文件里的专业技能提问角度。JD 可以调整提问优先级和深度，也可以带出少量简历未写、但 JD 明确重视的技术问题；这些问题标注“来自 JD”。只有输入包含专业技能条目时才补充这类题。保持 JD 题为少数，不让它淹没简历题。
4. 对每条具体工作，结合常见问题文件中的条目追问和简历内容，选择少量高价值问题，再沿原理、边界、取舍、验证深入；只有专业技能时参考文件中的专业技能问题。整体题与条目题、不同条目之间去重；候选人给出级别时据此调整深度。问题只从简历可见信息和常见面试话题出发，不用项目代码或文档反推隐藏细节。
5. **问题稿已保存后**，若选择回答模式，才读取相关代码、项目文档、补充说明或可靠的公开技术资料。只在原有主问题和追问下补回答，保留所有问题标题原文与顺序；材料中才出现的术语、实现或故障只能进入答案，不能成为新问题或追问。完成前对照已保存的问题稿检查标题。简历已写的职责、数据和结果可直接用于项目回答；未写的具体实现或细节需要材料支持，否则写“待补充”并指出缺少的信息。项目回答以候选人口吻表达；常见问题文件中的回答架构可用于组织答案。团队、流程、故障、冲突和个人收获等事实缺失时保留待补充位置。专业技能的通用技术事实可依据可靠资料，个人使用经历仍以候选人材料为准。版本相关结论说明适用版本或条件。

## 文档

- 项目/实习文档先放“整体经历”问题，再按输入条目分组；只有专业技能时直接按技能条目分组。每个主问题为标题，其下的追问为次级标题。只在特定回答后适用的追问，简短注明触发条件。
- **只要问题**：仅包含条目分组、主问题和追问，不附考察点、评分、答案或其他说明。
- **问题和回答**：每个主问题及追问下都附简短、可口述的参考回答；未获证实的个人事实标“待补充”。
- 除非用户指定其他路径，否则在调用时的当前工作目录下创建 `./resume/`（如不存在），先将纯问题稿保存为新的 UTF-8 Markdown 文件，回答模式再在同一文件中补入答案。文件名使用可区分的时间或序号；若重名则另取新名，不覆盖已有文档。不要把候选人的简历、代码、JD 或生成文档写入 skill 源码目录。完成后给出保存路径。
